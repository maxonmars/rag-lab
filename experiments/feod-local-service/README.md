# Локальная LLM как приватный сервис: доступ по сети, параллельность и лимиты

Задание девятого дня недели RAG: развернуть локальную LLM как сервис с HTTP API и чатом, проверить доступ по сети, стабильность
при нескольких запросах и базовые ограничения — rate limit и максимальный контекст
([ADR 0009](../../docs/adr/0009-local-llm-service.md)). Сервис — шлюз [servers/llm-gateway](../../servers/llm-gateway/README.md)
перед Ollama на этом же Mac: ключ, rate limit по ключу, один слот с очередью и лимит входного контекста в символах.
Демо — [docs/demos/local-service.md](../../docs/demos/local-service.md).

Разделы «Условия прогона», «Воспроизведение» и «Измерения» — вывод `curl`, лога шлюза и `rag citations`; «Вычислено» — арифметика над
ними; «Выводы» — оценки, они опираются на измерения и отделены от них.

## Воспроизведение

```bash
echo "GATEWAY_API_KEYS=$(openssl rand -hex 32)" >> .env       # затем тот же ключ в LAB_LLM_LOCAL_API_KEY
npm run gateway                                               # отдельный терминал
IP=$(ipconfig getifaddr en0); GATEWAY_KEY=$(grep '^GATEWAY_API_KEYS=' .env | cut -d= -f2)
curl -s -o /dev/null -w '%{http_code} %{time_total}\n' -H "Authorization: Bearer $GATEWAY_KEY" -H 'content-type: application/json' -d @experiments/feod-local-service/chat.json http://$IP:8787/v1/chat/completions
seq 8 | xargs -P 8 -I{} curl -s -o /dev/null -w '%{http_code} %{time_total} retry-after=%header{retry-after}\n' -H "Authorization: Bearer $GATEWAY_KEY" -H 'content-type: application/json' -d @experiments/feod-local-service/chat.json http://$IP:8787/v1/chat/completions
npm run dev:local -- --llm-local-base-url http://$IP:8787/v1 rag citations --rag-questions-file experiments/feod-citations/questions.md
cp .local/rag/rag-citations.md experiments/feod-local-service/rag-citations-gateway-1.md
```

Тела запросов для сценариев 8–10 собраны `node -e` из корпуса `.local/rag/corpus` (склейка `.md` в порядке имён, обрезка до нужного числа
кодовых точек, затем вопрос «Ответь одним словом: готово?») и из `docs/adr/*.md`. Фрагменты документации FEOD в отчёте —

## Вычислено

- Параллельные 5 и 8 запросов: интервал между завершениями 5×200 — 0.24–0.26 с, что совпадает со временем одиночного запроса `chat.json`
  (0.25–0.26 с). Запросы выполнялись последовательно, один слот.
- Граница контекста: символов на токен — 31500/8439 ≈ 3.73 и 32000/8563 ≈ 3.74 (английский корпус), 32000/9822 ≈ 3.26 (русский с кодом).
  Условие `prompt_tokens + 1024 ≤ 16384` для 32000 символов нарушилось бы при плотности ниже 32000/15360 ≈ 2.08 символа на токен;
  у замеренных текстов запас в 1.6–1.8 раза. Значение по умолчанию 32000 оставлено.
- Скорость обработки входа без кеша: 8563 токена за 71.4 с ≈ 120 токенов/с, 9822 токена за 82.4 с ≈ 119 токенов/с. Запрос на пределе 16384 токенов
  занял бы около 137 с без кеша — меньше таймаута 180 с, но не намного.
- `rag citations`: 0 ошибок модели из 10 при 20 запросах за 166.2 с (≈ 7 запросов в минуту при лимите 20). Медиана генерации
  17.7 с против 10.6–14.8 с (`params`, тот же шаблон `default`) и 11.0–14.5 с (`tuned`); длительность прогона 166.2 с против 116.0–130.2 с и 134.2–149.7 с.

## Выводы

Оценки, опираются на измерения выше.

- Шлюз выполняет задание на одной машине: ключ отсекает неавторизованные запросы (401), контекст сверх 32000 символов отклоняется до вызова
  Ollama за миллисекунды (413), лимит запросов даёт 429 с `Retry-After`, переполнение очереди — 503 с `Retry-After`, Ollama из сети не видна.
- Параллельность в сервисе ограничена одним слотом: пять одновременных коротких запросов дают ступени по ≈0.25 с, то есть запросы ждут
  друг друга; очередь из 4 и 503 защищают модель от перегрузки, а не ускоряют её. Поведение при одновременных длинных генерациях не измерялось.
- Лимит 32000 символов оставляет запас по токенам на обоих замеренных текстах, но основной риск — не контекст, а время: вход на пределе
  без кеша занимает 70–80 с на обработку, поэтому при `GATEWAY_UPSTREAM_TIMEOUT_MS=180000` запас по таймауту примерно двукратный.
- Прогон `rag citations` через шлюз прошёл без ошибок модели, 429 и 503, но медленнее прогонов без шлюза (медиана генерации 17.7 с против
  10.6–14.8 с). Причину по этим данным назвать нельзя: накладные расходы шлюза отдельно не измерялись, а во время прогона на той же
  машине шли `lint`, `typecheck` и другие проверки репозитория, поэтому сравнение со столбцами `params` — ориентир, не доказательство.

## Ограничения

- Одиночный прогон каждого сценария на одной машине; время зависит от прогрева модели и кеша Ollama.
- Второго устройства в LAN не было: сценарий 1 выполнен с этого же Mac по LAN-адресу. Доступность с другого устройства (в том числе
  правила файрвола macOS для `node`) не проверялась.
- Ollama запущена приложением Ollama.app без `OLLAMA_KEEP_ALIVE=30m`: приложение пользователя не перезапускалось. Модель оставалась
  загруженной, потому что запросы шли непрерывно; после простоя больше 5 минут первый запрос снова будет долгим (см. сценарий 1: 10.15 с).
- HTTP без TLS: ключ и тексты идут открытым текстом внутри LAN.
- Лимит контекста — в символах и приблизителен; плотный по токенам текст даст больше токенов на символ, чем замеренные три.
- Состояние rate limit и очереди живёт в памяти процесса и теряется при перезапуске (так в сценарии 7 лимит сбрасывается заменой процесса).
- Эмбеддинги в шлюз не ходят: `/rag on` и `rag citations` работают только на машине с Ollama.
- Сценарий 11 проверен на трёх репликах; длинная история в `/rag on` может превысить 32000 символов и получить 413 — такой диалог не проверялся.
- Лимиты `max_tokens` проверяются только в поле `max_tokens`; `max_completion_tokens` шлюз не разбирает и пробрасывает как есть.
