# Сценарии RAG-чата по документации FEOD

Два длинных диалога для `rag dialog` (ADR 0006). Каждый сценарий — раздел `## sN. Название`; поля:

- `Цель:` — цель диалога, её формулирует первая реплика пользователя;
- `Ключи цели:` — слова через запятую; цель сохранена на ходу, если каждое из них входит в цель из памяти задачи;
- `Память:` — необязательный список `- N: ключ`; ключ заведён пользователем в реплике N и с хода N должен оставаться в памяти;
- `Реплики:` — нумерованный список реплик пользователя в порядке диалога.

Ключи памяти взяты из реплик пользователя, а не из корпуса. Сравнение — подстроки после нормализации регистра, «ё», пробелов и
Markdown-символов; смысл памяти скриптом не оценивается. Каждый сценарий идёт в новом пустом диалоге.
На каждую реплику в корпусе есть ответ: задание требует ответа с источниками на каждом ходу. Отказы на вопросы вне корпуса
проверяет [feod-citations](../feod-citations/README.md). Часть реплик ссылается на сказанное раньше только через память задачи
(«наши слои», «наше ограничение», «наши договорённости»); итоговая реплика проверяет, что цель и договорённости не потеряны.

## s1. Миграция проекта с FSD на FEOD
Цель: перевести существующий frontend-проект с FSD на FEOD
Ключи цели: FSD, FEOD
Память:
- 2: TypeScript
- 6: deep imports
Реплики:
1. Привет! Мы хотим перевести наш frontend-проект с FSD на FEOD. Помоги разобраться по шагам.
2. Уточню: проект на TypeScript, около 40 страниц, сейчас слои FSD — app, pages, widgets, features, entities, shared.
3. С чего начать: какие верхние уровни есть в FEOD?
4. Куда при переезде деть наш слой shared?
5. А что код страниц может импортировать, а что ему запрещено?
6. Важное ограничение: deep imports в новом коде мы запрещаем сразу, без исключений.
7. Как тогда поступить с legacy deep imports, которые уже есть в проекте?
8. Где хранить API-клиент?
9. Во что превратятся наши слои entities, features и widgets?
10. Можно ли одному модулю импортировать другой модуль?
11. Чем вообще FEOD отличается от FSD — коротко, чтобы объяснить команде?
12. Как на code review проверять, что наше ограничение соблюдается?
13. Составь итоговый план миграции из 5 шагов с учётом наших ограничений.

## s2. Проектирование модуля корзины
Цель: спроектировать модуль корзины cart по правилам FEOD
Ключи цели: корзин, FEOD
Память:
- 3: public API
- 6: global
Реплики:
1. Я проектирую новый модуль корзины (cart) для интернет-магазина по FEOD. Помоги шаг за шагом.
2. Из чего должен состоять минимальный контракт модуля?
3. Договоримся о термине: под public API будем понимать только файл index.ts модуля.
4. Что модуль корзины должен экспортировать наружу, а что оставить внутри?
5. Корзине нужны данные товара из модуля catalog. Можно ли импортировать его напрямую?
6. Ограничение: общий код корзины и каталога мы не кладём в global.
7. Тогда что вообще можно хранить на уровне global?
8. А куда положить общие типы цены и форматирование цены?
9. Где хранить API-клиент для запросов корзины?
10. Как по правилам именования FEOD назвать модуль корзины и его публичные exports?
11. Как страницы будут импортировать корзину с учётом нашего термина?
12. Подведи итог: структура модуля cart с учётом всех наших договорённостей.
